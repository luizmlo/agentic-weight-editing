# Cost study: agentic weight editing vs fine-tuning

What does it cost to repair the loop defect with each method, and what does each repair cost every time the model
answers? Everything here is regenerated by `scripts/cost_accounting.py` into `data/cost.json`. Numbers as of
2026-11-08.

## Method

- **Agent tokens** come from the Claude Code subagent transcripts: the per-message `usage`, deduplicated by message id.
  The transcripts are local and not versioned; the extracted counts are in `data/cost.json`.
  - API-equivalent dollars use Anthropic list prices for Claude Opus 5.5: $4 / $20 per million input / output tokens,
    $0.20 for cache reads.
  - Cache writes are priced at 1.25× input (5-minute TTL) or 2× (1-hour TTL). The transcripts do not record which TTL
    was used, so we show both.
  - Nothing was actually billed. The runs used a Claude Code subscription, so the dollar column is a reference price,
    not money spent.
- **GPU-hours** are on the GTX 1660 SUPER, the only GPU used.
  - Agent runs: GPU time is estimated from the scorer ledgers as probes × 52 s plus gen-checks × 10.5 min. Both rates
    were measured on the naive-search run, which had the GPU alone and used its full budget: 40 probes and 6 gen-checks
    in 97.8 min.
  - E4: GPU time is the wall-clock time of each stage, with the GPU busy throughout.
- **Excluded from every arm:**
  - the dev48 confirmation run (0.4–1.1 GPU-h per candidate, needed by every method);
  - the supervisor's engineering, accounted separately below;
  - the one-time atlas build, which only the atlas arms use.

## Cost to produce the repair

| method | dev48 | GPU-h (1660S) | LLM tokens (context / output) | API-equivalent USD |
|---|---|---|---|---|
| base | 0.146 | — | — | — |
| **agent edit, protocol v2, no atlas (a1)** | **0.667** | **1.31** | 5.39 M / 47.5 k | 5.08–6.99 |
| agent edit, replicate (a2) | 0.646 | 1.30 | 6.86 M / 44.8 k | 5.95–8.26 |
| agent edit with atlas (r2 / r3) | 0.354 / 0.396 | 1.34 / 1.38 | 10.4 M / 73 k; 10.7 M / 57 k | 9.07–12.52 / 3.88–4.25 |
| naive search, same tools and budget (E3) | 0.271 | 1.63 | — | — |
| **LoRA-SFT on self-distilled traces (E4)** | **0.292** | **17.1** | — | — |
| decoding: logit bias, best of 3 | 0.521 | 4.41 for tuning all 5 decoding configs | — | — |
| decoding: budget forcing 4096, best of 2 | 0.479 | (same 4.41) | — | — |

E4 broken down: feasibility test 0.18 h; data generation 10.2 h (600 traces at a 6k cap, with 90% hitting the cap,
then 279 post-excision answers); training and export 6.3 h; epoch pick 0.5 h.

- **GPU:** the agent edit took **13× less GPU time** than LoRA-SFT. Counting the whole window in which the scorer held
  the GPU (about 2 h per run, whether busy or idle), the factor is still about 8×. The fine-tuning cost is dominated by
  data generation, and the defect itself makes that expensive: a looping model burns the token cap on most samples.
- **Quality:** the agent edit is 37.5 pp better on dev48, with 0 losses against 18 rescues. Spending more on the SFT
  recipe might close part of that gap (more samples per problem, more data, RL), but every one of those options costs
  more GPU time, not less.
- **Dollars:** on a GPU you own, the marginal cost is electricity, about 0.26 kWh per agent run against about 3.4 kWh
  for E4 (taking ~200 W at the wall). The trade becomes "$5–7 of agent tokens vs ~16 extra GPU-hours":
  - If a 1660S-class GPU-hour costs more than about $0.32–0.44, the agent is also cheaper in dollars.
  - On very cheap rented GPUs, E4 costs a few dollars less, but it delivers less than half the accuracy gain.
  - Faster GPUs shrink both GPU columns, so this break-even does not transfer to other hardware.

## Cost every time the model answers

The edit also makes the model cheaper to serve, because it stops looping. LoRA-SFT barely changes this.

| arm | dev48 mean tokens / problem | vs base | MATH-148 mean tokens | vs base |
|---|---|---|---|---|
| base | 11,714 | — | 11,788 | — |
| Astra edit | 9,404 | −20% | 11,098 | −6% |
| LoRA-SFT (E4) | 9,915 | −15% | — | — |
| budget forcing 4096 | 8,073 | −31% | 9,245 | −22% |
| **agent edit a1** | **4,729** | **−60%** | **8,399** | **−29%** |
| a1 + budget forcing | 3,772 | −68% | 7,089 | −40% |

At a 12k cap, a1 answers GSM8K-style problems with 2.5× fewer generated tokens than the base model, and with 2.1× fewer
than the LoRA. At any real serving volume, this recurring saving outweighs the one-time repair cost of either method.

## Comparison with the original agent (Astra, GPT-6)

Per-turn usage from the paper's public logs (`exp8_math/runs/*/turns/*/events.jsonl`):

| run | forward passes | turns | wall-clock h | input tokens (cached) | output tokens | MATH-500 (paper) |
|---|---|---|---|---|---|---|
| Astra p10c | 10 | 74 | 11.6 | 26.9 M (84%) | 1.11 M | 0.123 |
| Astra p25c | 25 | 86 | 8.5 | 38.4 M (90%) | 1.49 M | 0.141 |
| Astra p50c (the published edit) | 50 | 158 | 20.3 | 86.8 M (93%) | 2.91 M | 0.481 |
| **our a1** | 18 probes + 6 gen-checks | 64 | 2.1 | 5.39 M (88% cache reads) | 0.048 M | 0.466 (MATH-148, our sampler; Astra 0.209 here) |

a1 used about **16× fewer input tokens and 60× fewer output tokens** than the published Astra run, at about a tenth of
its wall-clock time. Under our sampler, a1's edit transfers better to MATH. The two setups differ in several ways, so
this is not a controlled comparison:
- different agent models and harnesses (Codex CLI vs Claude Code);
- Astra's forward passes were full generations on up to 512 problems at a 32k cap, on the authors' hardware;
- Astra's output count includes reasoning tokens;
- Astra worked from a CPU-only kernel over the weights.

It does show that Astra's scale of spending is not needed to find a strong edit for this defect.

## Overhead and totals

- **All agent runs**, the 6 runs plus 2 launches killed by the OOM daemon after about 2 minutes: 6.7 GPU-h and
  $31–40 API-equivalent.
- **The supervisor session** (Claude Code on Claude Opus 5.5, 2026-11-03 to 08) covers everything else: the PoCs,
  harness and scorer, briefs, audits, E1–E4 engineering, documentation and recovery from the power loss. It used
  78.2 M context tokens and 0.58 M output tokens, about $45–56 API-equivalent. It is shared by all arms, including the
  fine-tuning baseline, and is not attributed to any one of them.
- **Human time:** high-level direction and approvals only. It was not measured.

## Caveats

- One SFT configuration was tested. "AWE beats fine-tuning" is shown for this defect, this model and this recipe.
- GPU-hours are specific to a 6 GB Turing card without bf16 or tensor cores. On a modern GPU both columns shrink, and
  the ratio between them could change.
- API-equivalent prices are list prices on 2026-11-08. Subscription use has a different marginal cost.
- The agent's 1.31 GPU-h covers only the scorer's busy time; the 2 h wall-clock window is the upper bound. The 52 s and
  10.5 min rates come from one calibration run.
